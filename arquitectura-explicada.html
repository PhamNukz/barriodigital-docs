Qué se evalúa (y qué no)

Antes de la arquitectura, la restricción que la moldea. La pauta EP1 tiene solo dos indicadores, y ambos son sobre identidad y tokens, no sobre la infraestructura en sí:

60%

MSAL + Angular. Login/logout funcionan, guards e interceptor operan, se obtienen los tokens para consumir el API Gateway, y se leen roles y scopes desde los claims.

40%

BFF valida el token "al igual que el API Manager". Issuer, audience, firma, vigencia. Autorización por rol. Códigos de error correctos.

Todo lo demás — VPC, subredes, Oracle, RabbitMQ, Kafka, CI/CD — lo pide el caso (secciones 6–9) pero no la pauta. Por eso muchas decisiones abajo priorizan "que el flujo de tokens sea demostrable" por encima de "que la infra sea perfecta".

Por qué importa entender esto primero

Cada vez que hubo que elegir entre "más seguro/más correcto" y "más simple pero suficiente para la pauta", ganó lo segundo — y se documentó la alternativa. Ese patrón se repite en las secciones 2, 6, 7 y 9.

01

Siete contenedores de aplicación, tres servicios de infraestructura, cuatro máquinas EC2, un gateway administrado y un proveedor de identidad externo. Todo en una sola VPC con dos subredes.

Por qué los 7 corren en una sola EC2

Presupuesto. El Learner Lab da ~US$50–100 totales. Con -Xmx384m por JVM, siete contenedores caben en un t3.medium (4 GB). Separarlos por EC2 no aporta nada a la pauta y multiplicaría el costo. La red interna de Docker (http://requests:8081) hace que el BFF los alcance sin exponer puertos.

02

Red y zonas de seguridad

La VPC es una sola (10.0.0.0/16) con dos subredes en la misma AZ. La diferencia entre ellas no es el rango de IPs sino la tabla de rutas:

SubredCIDRRoute tableIP públicaQuién vive ahí
pública10.0.0.0/24rt-public: 0.0.0.0/0 → igw + localSí (auto-assign) + EIPec2-apps
privada10.0.1.0/24main: solo 10.0.0.0/16 localNoec2-mq, ec2-kafka, ec2-db
Por qué no hay NAT Gateway

Un NAT Gateway le daría salida a internet a las privadas (para apt, docker pull). Cuesta ≈ US$32/mes + tráfico, y en el Learner Lab eso es un tercio del presupuesto total. Además, que la base de datos no pueda salir a internet es una ventaja de seguridad, no un problema: aunque alguien comprometiera Oracle, no podría exfiltrar nada hacia afuera.

El costo real de esta decisión es operativo: las privadas no pueden instalar nada. De ahí el truco de la AMI.

El truco de la AMI

Una EC2 no se puede mover de subred. Y una EC2 en la privada no puede hacer docker pull. Entonces:

  1. Lanzar la instancia en la subred pública con el user-data que instala Docker.
  2. Entrar por SSH, hacer docker pull de las imágenes que va a necesitar (gvenzl/oracle-free:23-slim, rabbitmq:3.13-management, Zookeeper, Kafka, Kafka UI) y git clone de la infra.
  3. Create image → AMI con todo precargado.
  4. Lanzar desde esa AMI en la subred privada. Terminar la de la pública.

Resultado: máquinas que nunca han tenido ni tendrán ruta a internet, pero con todo lo que necesitan en disco.

Elastic IP

En Learner Lab las EC2 se apagan al cerrar cada sesión y la IP pública cambia en cada stop/start. La EIP 100.60.226.205 queda fija y asociada a ec2-apps. Es el único dato de red que aparece fuera de AWS: en la integración del API Gateway, en el ~/.ssh/config y en los secrets de CI/CD.

Detalle
Las IPs privadas (10.0.1.8, 10.0.1.254, 10.0.1.29) sí sobreviven al stop/start — la ENI las conserva. Solo se pierden si se termina la instancia. Por eso apps/.env puede apuntar a ellas directamente.

Acceso a las privadas: bastion

No hay forma de llegar a 10.0.1.x desde afuera. ec2-apps hace de bastion (salto): SSH a la EIP, y desde ahí SSH a la privada. En Windows ssh -J no reenvía la clave, así que se usa ~/.ssh/config con ProxyJump apps. Para las UIs (RabbitMQ :15672, Kafka UI :8085) se hace túnel:

ssh -L 15672:10.0.1.254:15672 -L 8085:10.0.1.29:8085 apps

La .pem vive solo en tu PC. Nunca en ec2-apps, nunca en git.

Un Security Group es un firewall stateful pegado a la instancia. La regla de diseño aquí es una sola: inbound mínimo, referenciando otros SGs en vez de rangos de IP. Outbound abierto (las privadas físicamente no pueden salir de todos modos).

Por qué "origen = sg-apps" y no "origen = 10.0.0.13/32"

Porque un SG como origen significa "cualquier instancia que tenga ese SG puesto". Si mañana ec2-apps se recrea con otra IP, o se agrega una segunda instancia de apps, la regla sigue funcionando sin tocarla. Un CIDR fijo se rompe. Es la diferencia entre describir quién puede entrar y describir desde dónde.

Lo que nunca
1521, 5672 ni 9092 abiertos a 0.0.0.0/0. Y los puertos 8081–8084 de los MS de dominio no se abren en sg-apps: aunque compose.yml los mapea al host, el SG los bloquea. Solo el BFF los alcanza, por la red interna de Docker.
Pendiente con fecha
El puerto 22 de sg-apps está en 0.0.0.0/0 desde el 11 hasta el 14 de septiembre para que ambos integrantes entren sin editar reglas cada vez que cambian de red. La auth es solo por .pem (password deshabilitado en la AMI), así que el riesgo real es bajo — pero el 14 vuelve a IPs concretas.
04

Identidad: Microsoft Entra ID

El sistema no tiene usuarios ni contraseñas propias. Toda la identidad la delega a Entra ID (antes Azure AD), que es el IDaaS que exige el caso. Angular usa MSAL para pedirle tokens; el backend solo valida tokens, nunca los emite.

Dos App Registrations, no una

El caso menciona una App Registration "BarrioDigital". Se usaron dos, siguiendo el patrón que recomienda Microsoft:

App RegistrationRolQuién la usaQué sale de aquí
barriodigital-apiRecurso protegido (la API)API Gateway, BFF, 4 MSAPI_CLIENT_ID = cdf23af8-…, scope access_as_user, los 4 App Roles
barriodigital-spaCliente público (el SPA)frontend-barriodigitalSPA_CLIENT_ID
Tenant—todosTENANT_ID = db9e57fc-…
Por qué dos

Separa quién pide el token (la SPA) de para quién es (la API). Con dos, el claim aud del access token es limpio: solo el GUID de la API. Se puede revocar o rotar la SPA sin tocar la API, y si mañana hay una app móvil, es otra App Registration cliente contra la misma API. Con una sola funciona igual, pero mezcla ambos roles.

Roles como claims

En barriodigital-api se definen 4 App Roles: Admin, Funcionario, Vecino, Auditor. Se asignan a usuarios en Enterprise Applications → Users and groups. Al hacer login, Entra mete el rol en el claim roles del token — y Spring Security lo convierte a ROLE_Admin, etc. (JwtRolesConverter).

El error más común
Un usuario sin rol asignado recibe un token sin claim roles. Todo endpoint con hasRole(...) responde 403. El token es válido, el login funciona, pero nada carga.

El manifest: requestedAccessTokenVersion: 2

Este es el detalle que rompe todo si falta. Entra emite tokens v1 por defecto. Los v1 tienen iss = https://sts.windows.net/<tenant>/ y aud = api://<guid>. Los v2 tienen iss = https://login.microsoftonline.com/<tenant>/v2.0 y aud = <guid> pelado.

Versiónissaud
v1.0 (default)https://sts.windows.net/<tenant>/api://cdf23af8-…
v2.0 (con manifest = 2)https://login.microsoftonline.com/<tenant>/v2.0cdf23af8-…
Por qué v2

El JWT authorizer de API Gateway se configura con un issuer y una audience. Se eligió v2 porque es el formato moderno y el que Spring (JwtDecoders.fromIssuerLocation) descubre solo. El ítem A8 del backlog fue exactamente este bug: los application.yml esperaban api://… y el token traía el GUID → 401. El fix fue aceptar ambos formatos en barriodigital.security.audiences.

05

Los tres tokens

MSAL recibe tres cosas al hacer login. Cada una tiene un dueño y un uso distinto, y confundirlas es la fuente típica de errores en la presentación.

TokenFormatoVidaContieneQuién lo usa
id_tokenJWT, aud = SPA~1 hname, preferred_username, oid, rolesSolo el frontend: roles.ts lee idTokenClaims.roles para mostrar el rol en la topbar y para guards
access_tokenJWT, aud = API60–90 miniss, aud, exp, nbf, scp = access_as_user, rolesMsalInterceptor lo pone en Authorization: Bearer. Lo validan Gateway, BFF y cada MS
refresh_tokenopaco24 h (SPA, no extensible)—Solo MSAL. acquireTokenSilent lo usa para renovar el access sin popup. Nunca sale del navegador
"Bearer" no es un token
Es el esquema del header Authorization (RFC 6750). "Token bearer" = "el access token enviado como Bearer".

¿Falta algún token?

No para este flujo. client_credentials (token de aplicación sin usuario) no aplica porque ningún servicio llama a la API sin usuario: notify/audit/report consumen colas, no HTTP. on-behalf-of sería si el BFF pidiera un token distinto para llamar a los MS — no hace falta, DomainClients reenvía el mismo access token y los MS lo validan con el mismo aud.

Por qué el BFF reenvía el mismo token en vez de pedir uno propio

Menos partes móviles. Un solo token con un solo aud que todas las capas entienden. Si el BFF hiciera OBO tendría que ser un cliente confidencial con secret, y ese secret tendría que vivir en la EC2. La pauta no lo pide y no mejora nada para este caso.

06

API Gateway

Es una HTTP API (no REST API): más barata, más simple, y es la única que tiene JWT authorizer nativo. El authorizer se llama entra-jwt y valida firma (contra el JWKS del issuer), iss, aud y exp antes de que la request toque tu EC2.

Las tres rutas

RutaAuthorizerIntegraciónPara qué
ANY /api/{proxy+}entra-jwthttp://100.60.226.205:8080/api/{proxy}La API. Sin token válido → 401 antes de llegar al BFF
ANY /{proxy+}ningunohttp://100.60.226.205/{proxy}Rutas de Angular (/requests, /catalog) → nginx devuelve index.html
ANY /ningunohttp://100.60.226.205/La raíz del SPA

HTTP API elige siempre la ruta más específica: /api/catalog/procedures cae en /api/{proxy+} (con JWT), no en /{proxy+}.

Por qué el frontend también pasa por el Gateway (y sin authorizer)

No estaba en el plan original. El plan era que el navegador cargara el SPA directo de http://<EIP> y solo las llamadas /api fueran al Gateway. Pero Entra ID exige que las redirect URIs sean https (salvo localhost), y http://100.60.226.205 no califica.

Las alternativas eran: certificado TLS en la EC2 (necesita dominio) o S3 + CloudFront (más piezas, más tiempo). La más barata: el mismo Gateway, que ya tiene HTTPS, sirve el SPA. Bonus: frontend y API quedan en el mismo origen (https://dnddhzpvgg.execute-api…), así que no hay CORS en producción.

Sin authorizer porque un SPA es HTML/JS estático y público por naturaleza — el login lo hace MSAL en el navegador. Lo que se protege es la data, y eso vive en /api/*. El nginx del frontend no proxea nada al BFF, así que /{proxy+} no es una puerta trasera.

Qué debe responder

# Sin token → el Gateway rechaza antes de llegar a la EC2
curl -i https://dnddhzpvgg.execute-api.us-east-1.amazonaws.com/api/catalog/procedures
# HTTP/2 401  {"message":"Unauthorized"}

# Con token válido
curl -i -H "Authorization: Bearer $TOKEN" .../api/catalog/procedures
# HTTP/2 200

# Con token válido pero sin rol Admin, en un endpoint solo-Admin → lo rechaza el BFF, no el Gateway
curl -i -X POST -H "Authorization: Bearer $TOKEN_VECINO" .../api/catalog/procedures
# HTTP/2 403  {"error":"acceso_denegado"}

# La raíz sin token → HTML de Angular (esperado)
curl -i https://dnddhzpvgg.execute-api.us-east-1.amazonaws.com/
# HTTP/2 200  <!doctype html>…

Estas cuatro respuestas son la evidencia de los dos indicadores de la pauta. El 401 lo da el Gateway; el 403 lo da el BFF.

07

Defensa en profundidad

Aquí está la decisión de arquitectura más importante, y la que hay que saber defender en la presentación.

El problema

API Gateway (HTTP API) llama a tu integración desde IPs de AWS que cambian y no están publicadas. No hay una lista que poner en el SG. Por lo tanto sg-apps tiene el puerto 8080 abierto a 0.0.0.0/0. Consecuencia directa: cualquiera que descubra la EIP puede saltarse el Gateway y pegarle al BFF a http://100.60.226.205:8080/api/….

Lo que lo resuelve

El BFF no confía en el Gateway. Revalida el JWT completo, exactamente igual: firma contra el JWKS de Entra, iss, aud, exp, y además scp y rol por endpoint — cosas que el Gateway ni siquiera mira. Y cada MS de dominio vuelve a hacerlo. Tres capas, cada una autosuficiente:

Capa 1
API Gateway
  • Firma (JWKS)
  • iss
  • aud
  • exp / nbf
→ 401 genérico
Capa 2

  • Todo lo anterior
  • scp = access_as_user
  • Rol por endpoint (hasRole)
→ 401 token_invalido
→ 403 acceso_denegado
Capa 3

  • Todo lo anterior, otra vez
  • Mismo Bearer reenviado

Capa 4

→ ORA-01017
Por qué esto es exactamente lo que pide la pauta

El indicador 2 (40%) dice literalmente que el BFF valide "al igual que el API Manager". No es redundancia por descuido: es la pauta describiendo defensa en profundidad. Si el BFF confiara ciegamente en el Gateway, el puerto 8080 abierto sería una vulnerabilidad real. Como no confía, es solo una superficie expuesta que rechaza todo lo que no traiga un JWT firmado por Entra.

La alternativa: VPC Link + ALB interno

Así se haría en producción para no exponer nada:

  1. VPC Link en API Gateway apuntando a subredes privadas y a un sg-vpclink. AWS crea ENIs dentro de la VPC.
  2. ALB interno en la privada con target group → ec2-apps:8080.
  3. La integración del Gateway apunta al ALB a través del VPC Link.
  4. ec2-apps se mueve a la privada, sin IP pública. sg-alb acepta 8080 solo desde sg-vpclink; sg-apps solo desde sg-alb.

Único camino: Internet → Gateway (JWT) → VPC Link → ALB → BFF. Nadie llega al BFF sin pasar por el authorizer.

Por qué no se hizo

ALB ≈ US$16/mes + NAT Gateway ≈ US$32/mes (al quedar todo privado, las EC2 necesitan NAT para docker pull y para bajar el JWKS de Entra) + el frontend tendría que ir a S3 + CloudFront. Contra ~US$50–100 totales de presupuesto y dos semanas de plazo, no vale la pena para algo que la pauta no evalúa. Queda documentado como la evolución correcta.

08

Datos y mensajería

Database per Service — con esquemas, no instancias

Una sola instancia Oracle Free 23 en ec2-db, con cuatro usuarios/esquemas: barriodigital_requests, _catalog, _audit, _report. Cada MS conecta con su propio usuario y solo ve sus tablas. Flyway crea las tablas al arrancar cada MS (V1__init.sql).

Por qué esquemas y no cuatro Oracle

Oracle Free necesita ≥ 2 GB de RAM. Cuatro instancias = cuatro t3.medium = cuatro veces el costo, por una separación que a nivel de aplicación ya existe: nadie escribe en la base de otro, y audit/report solo se enteran de lo que pasa en requests por Kafka, nunca leyendo su tabla. El compose lo marca explícitamente como ponytail: — si el caso exigiera instancias físicas separadas, es cambiar cuatro DB_HOST.

Gotcha corregido
El servicio de Oracle Free 23c es FREEPDB1, no XEPDB1 (que es de XE 21c). El .env.example tenía el viejo.

RabbitMQ: comandos

requests publica comandos (email, cuadrilla, certificado) a un exchange cmd.direct. Tres colas (q.cmd.email, q.cmd.crew, q.cmd.certificate), un consumidor (notify), y un cmd.dead.dlx para los que fallan. Dos nodos en cluster en ec2-mq.

Kafka: eventos

requests también publica eventos al tópico requests.events. Dos consumidores independientes: audit (arma el timeline) y report (arma los KPIs), cada uno escribiendo en su propio esquema. Tres brokers + tres Zookeeper en ec2-kafka.

Por qué dos sistemas de mensajería

Porque son dos patrones distintos y el caso pide ambos (secciones 8 y 9). RabbitMQ es para comandos: "manda este email", uno lo procesa, si falla va a DLQ. Kafka es para eventos: "pasó esto", N consumidores lo leen a su ritmo, el log se conserva y un consumidor nuevo puede reprocesar desde el inicio. Usar uno para lo del otro funciona, pero distorsiona el modelo.

Compose multi-host

El compose.yml original asumía que Rabbit y Kafka estaban en la misma red Docker (rabbitmq1, kafka1:9092). En tres EC2 eso no resuelve. Fix (ítem D9): RABBITMQ_HOST=10.0.1.254, KAFKA_BOOTSTRAP_SERVERS=10.0.1.29:9092,…:9093,…:9094, y en el compose de Kafka KAFKA_CFG_ADVERTISED_LISTENERS con la IP privada del host — si Kafka anuncia kafka1, el productor en otra máquina no sabe a quién conectarse.

09

CI/CD

La restricción
Learner Lab no permite crear IAM users ni OIDC providers, y las credenciales de sesión expiran cada ~4 h. GitHub Actions no puede hablar con AWS de forma estable: ni ECR, ni aws deploy.

Solución: sacar AWS del pipeline. Las imágenes van a GHCR (el registry de GitHub, gratis, autenticado con GITHUB_TOKEN automático) y el deploy es un SSH a ec2-apps que hace docker compose pull && up.

push / PR
ci.yml
  • mvn -B verify (6 MS)
  • npm run build (front)
  • Tests con H2 + JWT mock
push a main
build-image.yml
  • docker build
  • Push a ghcr.io/phamnukz/<repo>
  • Tags :latest y :sha
push apps/** o manual
deploy.yml
  • SSH a EIP con deploy key
  • Escribe .env desde secret
  • compose pull && up -d
ec2-apps
docker compose
  • Baja 7 imágenes de GHCR
  • Levanta con restart
Por qué los IDs de Azure y passwords no van en la imagen

La imagen es la misma para cualquier tenant y cualquier entorno. Todo entra por variables de entorno en runtime (application.yml lee ${AAD_ISSUER_URI}, etc.). Una imagen, N entornos. Los 7 repos de código no tienen ningún secret; solo barriodigital-infra tiene EC2_HOST, EC2_USER, EC2_SSH_KEY y APPS_ENV.

Por qué una deploy key dedicada y no la .pem

Si la .pem del key pair se filtra desde GitHub, hay que rotar las cuatro EC2. Una deploy_key ed25519 separada se revoca borrando una línea de authorized_keys.

Bloqueante
Los packages en GHCR tienen que estar en Public para que ec2-apps haga docker pull sin login. Solo el dueño de la cuenta puede cambiarlo (ítem G4).

El último tramo: deploy.yml

Hasta el 2026-09-13 el pipeline terminaba en GHCR: la imagen nueva llegaba al registry pero nadie la bajaba a la EC2 — el deploy era ssh apps a mano. deploy.yml en barriodigital-infra cierra el loop:

Se dispara conHace
push a main que toque apps/**SSH a la EIP → git pull de infra → escribe apps/.env desde el secret → docker compose pull && up -d --remove-orphans → docker compose ps
botón Run workflow (manual)

Un cambio de código en un MS no dispara el deploy (el push va a otro repo). El flujo es: push al MS → esperar build-image verde → Run workflow en infra. Automatizarlo requeriría un repository_dispatch con un PAT; para la prueba, el botón basta.

Los cuatro secrets (solo en barriodigital-infra)

SecretValorPor qué existe
EC2_HOST100.60.226.205La EIP. Si cambiara, es el único lugar en GitHub donde está
EC2_USERubuntuUsuario por defecto de la AMI
EC2_SSH_KEYclave privada deploy_key completa (-----BEGIN…END-----)Con qué entra Actions a la EC2. Ver abajo por qué no es la .pem

Por qué una deploy key y no la .pem

SSH acepta a cualquier clave privada cuya pública esté en ~/.ssh/authorized_keys del servidor. Puede haber varias. Hoy las 4 EC2 comparten el key pair barriodigital-key: una sola .pem abre todo.

Meter esa .pem en GitHub funcionaría — pero sería una tercera copia (PC tuyo, PC de tu pareja, GitHub) de algo que abre las cuatro máquinas. Si se filtra (un log de Actions que la imprime, un fork mal configurado), hay que rotar el key pair en las 4 EC2 y redistribuir la nueva.

Con una clave ed25519 generada solo para esto: su pública se agrega a authorized_keys de ec2-apps únicamente, la privada vive solo en el secret. Si se filtra, se revoca borrando una línea, y la .pem sigue funcionando. Y desde ec2-apps sin la .pem no se salta a las privadas. Mismo principio que los Security Groups: cada credencial con el alcance mínimo para su trabajo.

Paso a paso (PowerShell, EC2 prendida)

# 1. Generar el par dedicado
ssh-keygen -t ed25519 -f "$env:USERPROFILE\deploy_key" -C barriodigital-deploy -N '""'

# 2. Pública → ec2-apps (se agrega, no reemplaza)
Get-Content "$env:USERPROFILE\deploy_key.pub" | ssh apps "cat >> ~/.ssh/authorized_keys"
ssh -i "$env:USERPROFILE\deploy_key" ubuntu@100.60.226.205 "echo ok"

# 3. La EC2 necesita el repo clonado (no solo la carpeta apps/ copiada por scp)
ssh apps "cd ~ && git clone https://github.com/PhamNukz/barriodigital-infra.git"

# 4. Privada → portapapeles → secret EC2_SSH_KEY; luego borrarla del disco
Get-Content "$env:USERPROFILE\deploy_key" -Raw | Set-Clipboard
Remove-Item "$env:USERPROFILE\deploy_key", "$env:USERPROFILE\deploy_key.pub"

# 5. .env real → portapapeles → secret APPS_ENV
ssh apps "cat ~/apps/.env" | Set-Clipboard

Orden de los pushes cuando cambian infra y un MS a la vez: primero infra (para que la EC2 tenga el compose.yml nuevo), luego el MS, luego Run workflow.

10

Decisiones y trade-offs, en una tabla

Todo lo anterior, resumido como "qué se eligió, contra qué, y por qué". Es lo que hay que poder responder si preguntan.

HTTP API con JWT authorizer
vs REST API + Lambda authorizer
JWT authorizer nativo, más barato, sin código. REST API necesitaría una Lambda que valide el token a mano.
BFF expuesto en 8080 y revalidando JWT
vs VPC Link + ALB interno
Gateway no tiene IPs fijas; VPC Link cuesta ~US$48/mes en ALB + NAT. La revalidación en el BFF es lo que pide la pauta y neutraliza el bypass.
Frontend servido por el Gateway
vs http://EIP directo, o S3 + CloudFront
Entra exige redirect URI https. El Gateway ya tiene TLS. Mismo origen = sin CORS.
Dos App Registrations
vs una sola

Es un pass-through con seguridad: valida, decide por rol, reenvía. No mapea DTOs (Map<String,Object>), no cachea, no agrega lógica. Lo mínimo que la pauta pide de un BFF, sin inventar responsabilidades.

    report/kafka/ReportEventListener.java
Por qué AFTER_COMMIT y no publicar directo desde el service

Si TramiteService.crear publicara a Kafka antes del commit y la transacción luego fallara (Oracle caído, constraint), audit tendría un evento de un trámite que no existe. Con AFTER_COMMIT, el evento sale solo cuando la fila ya está en disco. El costo: si Kafka está caído justo después del commit, el evento se pierde (no hay outbox). A esta escala es aceptable y está documentado.

Por qué audit y report tienen groupId distintos

En Kafka, cada consumer group recibe todos los mensajes del tópico. Si audit y report compartieran grupo, se repartirían los mensajes y cada uno vería la mitad. Con grupos separados, cada uno ve el 100% y avanza a su ritmo — report puede estar caído una hora y al volver reprocesa desde donde quedó.

R5 · El resto de la máquina de estados

Cada transición repite R4 (sin la verificación de cupo, que solo corre en ADMITIDO). Lo que cambia es qué comandos salen a RabbitMQ — la regla vive en el switch de TramiteEventRelay.alCambiarEstado:

INGRESADO→ADMITIDO→EN_GESTION→EN_TERRENO→RESUELTO · desde cualquiera no terminal → RECHAZADO
Transición aKafka requests.eventsRabbitMQ (comandos)notify hace
INGRESADO (crear)sícertificate.gen"comprobante de ingreso"
ADMITIDOsíemail.sendemail ADMITIDO
EN_GESTIONsíninguno—
EN_TERRENOsíemail.send + crew.ticketemail VISITA_AGENDADA + ticket de cuadrilla con la dirección
RESUELTOsíemail.send + certificate.genemail RESUELTO + "certificado de resolución"
RECHAZADOsíninguno—

Cuando el trámite 7 llega a RESUELTO, report ya tiene 5 eventos de él. KpiService.tiempoResolucionPromedioMin busca el INGRESADO y el RESUELTO del mismo tramiteId y resta los timestamps. Ese es el KPI "tiempo promedio de resolución".

Por qué la máquina de estados es un enum con un mapa

El caso exige "no se puede pasar a EN_TERRENO sin ADMITIR". En vez de un if especial para eso, el grafo es secuencial: EN_TERRENO solo es alcanzable desde EN_GESTION, que solo es alcanzable desde ADMITIDO. La regla queda garantizada por construcción, no por una validación aparte que alguien pueda olvidar.

    Si el mismo Auditor luego pide /api/report/kpis: el BFF responde acceso_denegado sin llamar a report. Auditor lee el timeline, no los KPIs — "solo lectura, relevante para transparencia" (caso, línea 25).

Por qué esto es "analítica en tiempo real sin bloquear el core"

Mientras el Admin mira KPIs y el Auditor revisa timelines, requests no recibió ninguna llamada. Podría estar caído y las dos consultas responderían igual, con los datos hasta el último evento que llegó por Kafka. Y al revés: si report se cae, los vecinos siguen ingresando trámites — los eventos se acumulan en el tópico y report los procesa cuando vuelve, desde el offset donde quedó (groupId = "report-svc").

Eso es lo que pide el caso en la línea 34: "Datos por streaming (Kafka) sin bloquear el core". La alternativa — que report haga SELECT … FROM tramite GROUP BY contra la base de requests — acoplaría los dos servicios en la BD y rompería Database per Service.

Por qué el "tiempo real" es aproximado

Entre que requests hace commit y report tiene la fila hay latencia: AFTER_COMMIT → Kafka → consumer → insert. Milisegundos normalmente, segundos si Kafka está lento. El KPI puede ir un evento atrás de la realidad. Para un panel comunal es irrelevante; para un saldo bancario no lo sería. Es consistencia eventual, y es el precio de no bloquear el core.

Resumen: cuántas veces se valida un token

En R4 (admitir), el access token del funcionario se valida cuatro veces en una sola operación: Gateway → BFF → requests → catalog (por la llamada MS-a-MS del cupo). Cada capa baja el JWKS una vez y lo cachea, así que el costo es de CPU, no de red. Es redundante a propósito: ninguna capa asume que la anterior existió.

Glosario rápido

Red

VPC — tu red privada dentro de AWS. Subred — un rango de IPs dentro de la VPC; pública o privada según su tabla de rutas. IGW — Internet Gateway, la puerta de la VPC a internet. NAT Gateway — deja que instancias sin IP pública salgan a internet (no entren). EIP — IP pública fija que sobrevive a stop/start. ENI — la interfaz de red virtual de una instancia; conserva la IP privada. SG — Security Group, firewall stateful por instancia. Bastion — máquina pública usada como salto SSH hacia las privadas.

Gateway

HTTP API — el tipo simple/barato de API Gateway. JWT authorizer — valida el token contra un issuer antes de llamar a la integración. Integración — el backend al que una ruta reenvía. {proxy+} — comodín que atrapa cualquier path restante. Stage — un despliegue de la API; $default auto-despliega. ARN — Amazon Resource Name, el identificador único de cualquier recurso.

Identidad

IDaaS — identidad como servicio (Entra ID). MSAL — la librería de Microsoft para pedir tokens desde el navegador. App Registration — la identidad de una app en Entra. Scope (scp) — permiso delegado que la SPA pide sobre la API. App Role (roles) — rol asignado a un usuario, viaja como claim. JWKS — las claves públicas del issuer para verificar firmas. PKCE — extensión de OAuth para clientes públicos sin secret. iss / aud / exp / nbf — quién emitió, para quién, hasta cuándo, desde cuándo.

Aplicación

BFF — Backend for Frontend, la única API que el SPA conoce; orquesta los MS de dominio. Flyway — migraciones de BD versionadas que corren al arrancar. DLQ — dead letter queue, donde van los mensajes que fallan. GHCR — GitHub Container Registry. AMI — imagen de máquina, snapshot de una EC2 para clonarla.
