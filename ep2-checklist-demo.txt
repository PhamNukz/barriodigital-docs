[ ] CONFIRMAR LA IP PUBLICA DE ec2-apps
    Si no son Elastic IPs, la IP publica CAMBIA en cada stop/start. Las
    integraciones del Gateway la tienen escrita a mano, asi que despues de

    asociar Elastic IPs y no volver a tocarlo.

[ ] ESPERAR ~90 SEGUNDOS
    Los 8 contenedores arrancan a la vez en 2 vCPU y cada JVM tarda ~80s.
    Durante ese rato /api/... da 503. No es una falla, es el arranque.
    OJO: eso NO aplica a  /  -- ahi hay nginx sirviendo estaticos, levanta
    en un segundo. Si  /  da 503, no es warm-up, es que el Gateway no llega
    a la EC2 (ver el punto de la IP publica).

[x] CREAR LA RUTA QUE FALTA  (vale 7% de la nota)  -- HECHO el 15-10
    API Gateway > barriodigital-api > Routes > Create
      Metodo:  OPTIONS
      Path:    /api/{proxy+}
      Adjuntar la MISMA integracion que usa ANY /api/{proxy+}
      NO adjuntarle authorizer
    Sin esta ruta, el preflight CORS responde 401. Con ella responde 200:
    lo contesta el BFF (Spring da 200 a un preflight valido, no 204), y lo
    que importa son los headers access-control-allow-*.

[ ] CONFIRMAR QUE EL 8080 DE sg-apps ESTA EN 0.0.0.0/0
    El API Gateway no tiene IP fija. Si alguien restringe el 8080 a una IP
    /32, TODO /api/... da 503 por el Gateway aunque desde tu PC el 8080
    responda (paso el 15-10: estaba restringido a la IP de un PC).

[ ] VERIFICAR QUE TODO RESPONDE  (comandos en la seccion 3)
    Los 4 curls deben dar: 200, 401, 401, 200

3. COMANDOS LISTOS PARA PEGAR
===============================================================================

NOTA: la terminal local es PowerShell. Las variables se declaran con
      $VAR = "valor"  (no  export VAR=valor, eso es bash) y hay que envolver
      la URL en comillas dobles para que se expanda. El nulo es NUL, no
      /dev/null. Y siempre  curl.exe , porque  curl  a secas en PowerShell
      es un alias de Invoke-WebRequest y no entiende estas banderas.


--- Variable base (pegar primero en la terminal local) ---

$GW = "https://dnddhzpvgg.execute-api.us-east-1.amazonaws.com"


--- Verificacion previa (los 4 deben dar 200, 401, 401, 200) ---

curl.exe -s -o NUL -w "frontend: %{http_code}\n" "$GW/"

curl.exe -s -o NUL -w "sin token: %{http_code}\n" "$GW/api/requests"

curl.exe -s -o NUL -w "token basura: %{http_code}\n" -H "Authorization: Bearer no.es.un.jwt" "$GW/api/requests"

curl.exe -s -o NUL -w "preflight: %{http_code}\n" -X OPTIONS "$GW/api/requests" -H "Origin: http://localhost:4200" -H "Access-Control-Request-Method: GET"

  (No partir las lineas con  \  al final: eso es bash. En PowerShell el
   continuador es el acento grave, pero es mas seguro dejarlas en una linea.)


--- Sacar el access token del navegador (mucho mas rapido que buscarlo a mano) ---

  Inicia sesion en la app, abre DevTools > Consola y pega esto:

copy(Object.values(localStorage).map(v=>{try{return JSON.parse(v)}catch(e){return null}}).find(o=>o&&o.credentialType==='AccessToken')?.secret)

  Queda copiado en el portapapeles. Luego, en la terminal:

$T = "<pegar aqui>"          # token de Admin o Funcionario
$AUDITOR = "<pegar aqui>"    # token de Auditor (para demostrar el 403)


--- Las tres respuestas del JWT (el corazon de la demo) ---

# 1. Sin token -> lo rechaza el GATEWAY, ni llega al backend
curl.exe -i "$GW/api/requests"

# 2. Con token valido -> 200 y el JSON del microservicio
curl.exe -i -H "Authorization: Bearer $T" "$GW/api/requests"

# 3. Token valido pero SIN el rol -> 403, lo rechaza el BFF
#    El cuerpo JSON va en un archivo: PowerShell destroza las comillas dobles
#    cuando pasa  -d '{"a":"b"}'  a un .exe. Con @archivo no hay sorpresas.
'{"nombre":"Prueba","requisitos":"x","cupoDiario":5}' | Set-Content -Encoding utf8 body.json

curl.exe -i -X POST -H "Authorization: Bearer $AUDITOR" -H "Content-Type: application/json" -d "@body.json" "$GW/api/catalog/procedures"


--- Mostrar que todo esta desplegado y activo ---

  El  --%  le dice a PowerShell "de aca en adelante no interpretes nada",
  asi las comillas y las llaves de --format llegan intactas a ssh.

ssh apps  --% docker ps --format "table {{.Names}}\t{{.Status}}"
ssh mq    --% docker ps --format "table {{.Names}}\t{{.Status}}"
ssh kafka --% docker ps --format "table {{.Names}}\t{{.Status}}"

4. LOS 7 PUNTOS DE LA PAUTA, MAPEADOS
===============================================================================

(1) "Mostrar en la plataforma cloud la creacion de la instancia de API Manager
     en funcionamiento"

    -> Pestana 2 (API Gateway). Mostrar que la HTTP API existe, su Invoke URL
       y el Stage $default con auto-deploy.
    -> Para "en funcionamiento": la app de la pestana 1 esta cargando A TRAVES
       de esa misma URL. Eso ya lo demuestra.


(2) "Mostrar la configuracion del API Manager que permite llamar a los
     endpoints del backend"

    -> Pestana 2 (Routes) + pestana 3 (Integrations).
       Ruta  ANY /api/{proxy+}  ->  integracion  http://<EIP>:8080/api/{proxy}
    -> Decir por que es {proxy+} y no una ruta por endpoint: detras hay un BFF,
       no los microservicios sueltos. El Gateway autentica y pasa; quien enruta
       a requests/catalog/audit/report es el BFF.


(3) "Demostrar que el frontend consume los endpoints a traves del API Manager"

    -> Pestana 1 con DevTools > Red. Navegar a Tramites.
       Mostrar que las peticiones van a dnddhzpvgg.execute-api...
       y que llevan el header Authorization: Bearer.
    -> Clave: la URL del XHR es la del Gateway, no la IP de la EC2.


(4) "Mostrar que el API Manager valida JWT, rechazando invalidas y aceptando
     las correctas"

    -> Terminal #2, los tres comandos de la seccion 3.
       401 sin token / 401 con token basura / 200 con token valido.
    -> Y el 403 como bonus: token VALIDO pero sin el rol. Explicar la
       diferencia — 401 es "no se quien eres", 403 es "se quien eres y no
       puedes". El 401 lo da el Gateway, el 403 lo da el BFF.


(5) "Mostrar la creacion del tenant en IDaaS y la existencia de usuarios
     registrados"

    -> Pestana 5 (tenant y Tenant ID), pestana 6 (los usuarios),
       pestana 7 (cada usuario con su App Role asignado).
    -> Si preguntan por el auto-registro: las cuentas se aprovisionan desde el
       tenant porque es un padron municipal — un vecino no se auto-registra, se
       valida contra el registro civil. El auto-servicio requiere Entra
       External ID, que es otro tipo de tenant.


(6) "Demostrar que el frontend utiliza OAuth 2.0/OpenID Connect para iniciar
     sesion y obtener un JWT valido"

    -> Pestana 1, con DevTools YA ABIERTO en Red, sesion cerrada.
       Hacer login. Filtrar por "authorize" y mostrar en la peticion:
         response_type=code        -> Authorization Code, no Implicit
         code_challenge + S256     -> PKCE
         state y nonce             -> anti-CSRF y anti-replay
       Despues el POST a /token con el code_verifier.
    -> Copiar el token y pegarlo en jwt.ms (pestana 9) para mostrar los claims:
       iss, aud, roles, scp, exp.


(7) "Mostrar en la nube que el backend y el frontend estan desplegados,
     activos e integrados"

    -> Pestana 4 (EC2): las 4 instancias en "running".
    -> Terminal #1: los tres  docker ps  de la seccion 3.
       8 contenedores en apps (con rabbitadmin), 2 en mq, 7 en kafka.
    -> "Integrados": crear un tramite en la app y que aparezca en la tabla.
       Eso recorre frontend -> Gateway -> BFF -> requests -> Oracle.

5. SI ALGO FALLA EN VIVO
===============================================================================

  503 en  /  (la pagina no carga)
    -> NO es warm-up: el frontend es nginx, levanta al instante. El 503 lo
       genera el Gateway porque no alcanza la EC2. Casi siempre: la IP
       publica cambio en el ultimo stop/start y la integracion quedo vieja.
       Confirmarlo con  curl.exe -i "$GW/"  -- si la respuesta trae headers
       x-amzn-* y ningun  Server: nginx , fallo el Gateway, no la app.
       Despues: comparar Public IPv4 de ec2-apps con el URI de la integracion.
       Si coinciden, mirar el Security Group (80 y 8080) y  ssh apps 'docker ps'.

  503 en  /api/...  pero  /  carga bien
    -> Si las EC2 recien partieron, es warm-up: las JVM siguen arrancando.
       Esperar. Si pasan 2 minutos, revisar con:  ssh apps 'docker ps'
    -> Si los contenedores llevan rato arriba: revisar que el 8080 de
       sg-apps tenga origen 0.0.0.0/0 (ver seccion 1).

  El login no abre el popup
    -> El navegador lo bloqueo. Permitir ventanas emergentes para el sitio.

  401 en TODAS las llamadas despues de loguearse
    -> El token expiro (duran ~60-90 min). Boton "Renovar" en la topbar,
       o cerrar sesion y volver a entrar.

  Un curl con $T da 401
    -> El token que copiaste expiro o es el de otra cuenta. Volver a copiarlo
       con el comando de la seccion 3.

  Regla general: si algo falla, decirlo y seguir. Intentar arreglarlo en vivo
  consume los 10 minutos. Es mejor: "esto normalmente responde X, debe ser el
  token expirado" y pasar al siguiente punto.
